# alpha-0.194

## 「打断 + 合并重新理解」：生成期间的新消息不再排队

### 背景（朋友环境实机日志实证）

2026-10-01 21:31 的会话里：用户发「晚上吃」→ 防抖结算（21:31:30）→ 生成完成（21:31:41）→ **润色直到 21:32:48 才结束**（单步 67 秒）→ 期间 21:31:46 用户又发「饭了吗」→ 只能**另起一轮排队**（21:32:49 才开始生成、21:33:00 才入发送缓冲）。结果就是"只回了上一句，下一句慢且含糊"。

排查结论：**「生成中被新消息打断 / 结算后新消息并回上一轮重新理解」这套机制此前并不存在**——已有的只是「防抖收集」「发送缓冲逐条发」「抢话裁决（仅针对已入缓冲、待发的消息）」。本次按用户裁断补齐。

### 改动

1. **润色不再保留思考 + 加超时（性能根因）**
   - `reply_polish`：`_disable_thinking=False`（保留思考）→ **True**；并加 `rewrite.timeout_seconds`（默认 25 秒，5–120）超时保护，超时/失败回退原回复。67 秒级卡顿消除。
2. **会话级「生成中」状态 + 打断合并（覆盖：接管改换 / 接管走主链）**
   - `_inflight`（会话 → `{started, pending, restarts, mode, first_text}`，TTL `send.inflight_ttl` 默认 180 秒防残留）。
   - **接管改换**：`on_llm_request` 若该会话正在生成 → 本轮**不排队、不生成**，把文本并入 `pending` 并静默阻断；当前轮生成完成后发现 `pending` 非空 → **作废本轮结果**，把新内容并入 system（`【对方又补充说了】…只回一条，先照顾最新的一句`）**重新生成**，最多 `send.max_restarts` 次（默认 2，达上限直接发当前回复，避免永远不回）。
   - **接管走主链**：主链回复无法中途打断，改为在 `on_llm_response` 检测到 `pending` 时**作废本轮回复**（`completion_text=""`、`result_chain=None`）→ 用合并文本**补发一次**（接管式直连），保证用户最后说的话一定被回应到。
   - **未覆盖（如实备注）**：`放行` / `监视` 模式生成发生在 AstrBot 主链内部，插件无法打断（要打断就得改成"临时阻断+自己重放"，会改变这两种模式的语义）；`阻断`模式本就不生成。如需覆盖，另行确认。
3. **抢话策略默认改为「作废重理解」（旧裁决保留可选）**
   - 新配置 `send.interrupt_mode`：`作废重理解`（默认）/ `模型裁决`（旧 A 说完再回、B 憋回去重组织）/ `提速发完`。
   - 「作废重理解」= 丢弃还没发出的部分，并把**已经真正发出去的回复**（`_send_item` 成功即记录，取用后清）与"没说完的话"一起并入下一轮生成上下文（`你刚才已经回过这些，别重复也不要当成没说过：…`）——避免用户指出的"空档期影响判断"。

### 新增配置

| 模块 | 键 | 默认 | 说明 |
|---|---|---|---|
| send | `interrupt_mode` | 作废重理解 | 抢话处理：作废重理解 / 模型裁决 / 提速发完 |
| send | `max_restarts` | 2 | 生成期间连续被打断时最多重生成几次 |
| send | `inflight_ttl` | 180 | 「正在生成」判定窗口(秒)，防异常残留误判 |
| rewrite | `timeout_seconds` | 25 | 润色单条超时(秒)，超时用原回复 |
