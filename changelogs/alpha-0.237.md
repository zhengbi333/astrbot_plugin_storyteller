# alpha-0.237

## 修「嘴上说发了表情包，实际什么都没收到」

### 现象（用户朋友实测，QQ 端）

对方说「你能给我发张表情包吗」→ 模型回：
「要表情包啊……你倒是会挑时候。/（翻了翻相册 / 随手甩过去一张刚存的“猫猫炸毛”jpg）喏 / 就这张 / 够你用的了～」
—— **但一张图都没有真的发出去**；过了一段时间才收到一张表情包（那张是**表情包判定**这条正常流程后续补的，不是回应索要）。

### 查证（先确认能力本身没坏，再定根因）

| 检查 | 结果 |
|---|---|
| 发图能力是否存在 | 存在，且有两条通道：原生工具 `story_emoji_send`（主链/接管均可用）、文本协议 `[DO:emoji_send]{...}` |
| 图库为空时会不会不给这个工具 | 不会，`available_capabilities()` 不做图库判断（工具始终提供） |
| `[EMOJI:分类]` 何时变成真图 | **发送组装时**才渲染（`EmojiStore.split`）→ 定稿后补标记仍然发得出去 |
| 那次的真实路径 | 模型**没有调用任何工具**，只在文字里描述了「已经发送」→ 用户收不到 |

### 根因

提示里的约束太泛（原有「别只在嘴上答应」「不要假装已经做了」），**没有针对「发图」的具体规则**；
`emoji_send` 的工具描述也只是软性的「想表达情绪时用」，没说「对方要就必须调用」。

### 修复

1. **工具描述写死规则**：`emoji_send` 描述改为「对方明确要表情包/要图时**必须调用本工具**；不要只在文字里写『给你发了/甩过去一张』——那只在文字里，用户收不到图」。
2. **文本协议清单**新增具体规则：「写『给你发了一张』而没调用工具 = 用户什么都没收到」。
3. **兜底补发**（关键）：回复里「声称已经发出图片/表情包」但本轮确实没有发送时，自动从图库补一张（追加 `[EMOJI:分类]`，发送时渲染成真图）。检测逐句进行，**句中带未来词（回头/下次/明天/待会…）不算**——那是承诺，交给承诺识别处理；同时尊重 `emoji.enabled` 开关、对方 opt-out、已有表情包标记不重复补。
4. **图库为空时告知模型**（brief 与完整清单两个分支都覆盖）：「现在没有任何表情包/图片可用——不要描述发图、也不要答应发图片」，避免空库时继续假装。

### 一处设计取舍（避免倒退）

那条较长的发图规则**只进文本协议分支**：原生工具模式下它由**工具描述**承担（工具 schema 本来就要随请求发出，不额外占 system）。这正是 0.206「把 system 从 3702 压到 1747 字」的成果——若塞进简要文案会把那段从约 150 字撑到 233 字，`test_iter22` 的「简要模式 < 220 字」当场就会失败（本轮确实先失败了一次，据此才改为现在的分置方案）。

`随手甩过去一张刚存的“猫猫炸毛”jpg）喏` → **命中**（会补发）；
`回头给你发一张图` / `明天整理好发你` / `你想让我发张表情包？` → **不命中**（是承诺或询问，不补发）。
