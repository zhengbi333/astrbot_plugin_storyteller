# alpha-0.96

> 本版基于**直连上游实测**（用用户新 Key 原样调用两家提供方）得出的结论开发：
> 「生成日程慢/超时」的真凶 = **推理模型默认长时间思考**（45 秒+、动辄数分钟、烧数万 Token），
> 而网络与 Key 完全正常（同一模型回答"你好"仅 0.8~2.8 秒）。
> 实测加一个通用参数 `{"thinking":{"type":"disabled"}}` 后，同一提示词两家均降为 **0~16 秒出正文、10~20 秒整体完成**。

## 直连上游通道（新设置项 models.direct_enabled，默认开）

- 对 OpenAI 兼容提供方：从 provider 对象提取 base_url/api_key/model（防御性读取，无任何提供方特判），
  插件自建 httpx 请求直连上游，**绕开 AstrBot 客户端写死的超时墙**
  （SDK 超时在客户端创建时定死：实测硅基流动 30 秒、官方 120 秒，非流式必撞）。
- 任何一步拿不到直连信息（非 OpenAI 兼容 / Azure 等特殊认证形式）或直连失败，
  **自动回退原通道**（原有流式+限时+重试+回退非流式逻辑不受影响）。
- 直连与 AstrBot 通道共用同一套聚合逻辑（快照去重 / 思考风暴早停 / 内容超长早停），
  usage 转成统一协议（token 记账兼容）。

## 关闭思考（新设置项 models.disable_thinking，默认开）

- 直连时附带通用「关闭思考」参数 `{"thinking":{"type":"disabled"}}`（DeepSeek 官方标准格式，各主流 OpenAI 兼容服务通用），
  结构化生成（日程/穿搭/状态/判断/衣柜）从此 **10~20 秒完成**，不再等模型空想。
- **提供方不认该参数（HTTP 400/422）→ 自动去掉参数重试一次**，绝不报错，兼容任何一家。
- **创作类调用已显式保留思考**（`_disable_thinking=False`）：接管回复、重写润色、回复润色、
  做梦/思考、风格生成、人格生成、主动对话、日记——对话质感与想象力不受影响。
- 两个新设置项的提示文案已写明**利害关系**（影响面、为何需要、关闭后果）。

## 生成预算保险丝（max_tokens，直连通道专属）

- 查证结论：示例插件（private_companion）大量使用 `max_tokens`，但 **AstrBot 的 OpenAI 兼容路径会吞掉该参数**（`_prepare_chat_payload` 只组装 messages+model）——示例插件传了等于没传，其"效果好"的真实原因是任务短（短对话思考量小、秒级完成）+ 失败静默兜底。
- 我们的**直连通道**能真正把 `max_tokens` 发出去（OpenAI 兼容标准参数）。语义：**生成预算硬上限**——正常输出在预算内自然收尾；仅当模型跑飞超写时才被截断（finish_reason=length），由解析/重试兜底。它不是"让内容变短"的开关（长短靠提示词要求），而是防跑飞的保险丝。
- 已接线：日程 `_max_tokens=4000`、穿搭 `2000`、衣柜 `6000`、状态 `800`（正常输出远低于此，仅防跑飞）。

## 排查结论沉淀（供后续参考）

- AstrBot 客户端超时 = provider source 配置的 timeout（硅基 30s/官方 120s），非流式必撞、流式按块不受限；
- 直连实测（用户新 Key）：两家「你好」基线 0.8~2.8s 完成 → 链路无延迟；
  两家的「日程原题」思考 45s+ 未完成 → 慢在模型思考；
  加关闭思考参数后 10~20s 完成 → 参数即解法；
- 示例插件（private_companion）的方案是「模型分级路由 + max_tokens 限制 + 任务级超时」，
  **没有**关闭思考处理；其前提是手头有非推理模型可分流——用户环境全是 V4 推理系，不适用，
  故本插件采用「同一模型上关思考提速」的通用方案。
