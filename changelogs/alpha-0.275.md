# alpha-0.275

## P1-7：对方只回「嗯嗯」时，多带一轮上下文

**问题**：你说「我下周要去杭州出差」，她答完；你只回「嗯嗯」——
她看到的上下文里只有那个「嗯嗯」，**不知道你在应什么**，容易答得牛头不对马嘴。

**做法**：对方这条消息**不超过 N 字**时，上下文多取一轮。

- `intercept.short_reply_chars`，默认 **6**（「嗯嗯」「哦」「好的」都算），**0 = 关闭**；
- 实现上就是把 `rounds + 1`，多取 6 条再按轮截断；
- **不写死「嗯嗯」这个词** —— 用长度判断，因为「哦」「行」「知道了」都是同一类。

## P1-8：上下文带编号

每一行变成：

```
[1] 他：我下周要去杭州出差
[2] 我：去几天
[3] 他：嗯嗯
```

- `intercept.timeline_numbering`，默认**开**；
- 守则（`reference` 节）加了一句说明：
  **「想专门回某一条可以说「回 [2]」；编号只在这一轮有效，不是消息 ID。」**
- 编号在按轮截断**之后**才加，所以编号永远从 1 连续到 N，不会跳号。

## 验证（`audit_91_short_reply_numbering.py` 21/21）

- **A**：两项配置都在、默认值正确、都有 hint；
- **B**：「嗯嗯」/「哦」/「好的」/「我知道了」→ 算短；「我下周要去杭州出差」/ 空 → 不算；
- **C**：`short_reply_chars=0` 时一律不算（**能关**）；
- **D**：**实测取条数** —— 正常时取 30 条（4 轮×6+6），短回复时取 36 条（5 轮×6+6），确实多取了；
- **E**：开编号时有 `[1]`/`[2]`，关编号时没有；
- **F**：守则里确实有编号说明，且写了「只在这一轮有效」。

## 又一次踩到 falsy 陷阱

测试里我写的 `Cfg.int` 是 `int(self.get(k, default) or default)` ——
**`short_reply_chars=0`（表示关闭）被 `or` 吃成了 6**，导致 C1 失败。

这跟上一轮 `battery=0` 是同一个坑：**0 是合法值，不能用 `or` 兜底**。
已改成显式判 `None`。产品代码里我也顺手检查了一遍，`_is_short_reply` 用的是
`int(self.config.int(...) or 0)`，0 和 None 都落到 0，是对的。

## 已知边界

- 短回复判断只看**长度**，不看语义（「我不去」四个字也会多带一轮）—— 多带无害，不做语义判断；
- 编号只给「上下文」这一段，不给 `{当前说话}`；
- 记忆检索的 query 暂时还只用当前这条消息。要改成「上一句 + 这一句」需要动记忆插件的注入接口，
  本轮没做（跨插件，单独一轮更稳）。
